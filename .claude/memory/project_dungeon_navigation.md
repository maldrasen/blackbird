**SUPERSEDED 2026-09-20 by [[project-grid-movement-task215]]:** the room-based movement API described below (moveToFeature/moveToRoom, walkPath, room pathfinding, click-to-move) was deleted. Movement is now tile based through `DungeonNavigationSystem.step()`. Still true: Angband-style stairs (arrive on stairs of the direction you came from, fresh floor each time) and flat-color highlights.


Task 018 (dungeon navigation) finished 2026-07-14; refactored to room-based navigation 2026-07-15. Contracts that matter when extending:

- **Rooms, not features, are the unit of navigation.** Every room has a floor-global index (assigned in `DungeonFloor.addFeature`); `location`, `revealed`, door `from`/`to`, `stairs.roomIndex`, and the floor grid cells are all room indices. The feature is reachable from any room via `floor.getFeatureForRoom(index)` / `room.getFeatureIndex()` (needed for future first-arrival-in-feature events). Multi-room features exist (`nested-room`): internal doors are authored as plain specs on the Feature (feature-local position, from/to = ordinals into the feature's rooms), converted to floor doors by `FloorFactory.buildFeatureDoors` — edges join the graph before corridors, door records join after trimming so authored doors are never trimmed. Doors are plain `{ position, direction, from, to }` objects (the Door model was deleted 2026-07-16). DoorFinder skips same-feature adjacencies. Rooms of a multi-room feature are single overlapping boxes: later rooms overwrite their grid tiles (registration order matters) and render above earlier ones. Unrevealed rooms use a `.room.unrevealed` class (NOT the global `.hide`) — they render floor-colored (#111) instead of display:none so nested rooms don't leave holes; stairs are display:none inside them. Z stacking (reworked in task 120): unrevealed rooms `10 + var(--depth)`, hanging doors 30, revealed rooms `40 + var(--depth)`, doors 100 (see [[project-door-placement]]). Stair eligibility is opt-in per room via `room.allowStairs()` / `stairsAreAllowed()` (set by the feature type builders; nested-room allows only the inner room). `setLevel(level, arrival, theme)` / `enterDungeon(theme)` accept a forced theme; the dungeon fixture pins `'dungeon'`.
- `DungeonNavigationSystem.moveToRoom(index)` returns `{ encounter, revealed }` (`revealed` = this move revealed the room) — the system rolls (20% unexplored / 2% revealed, hardcoded pending theme-defined rates) but the **view** starts the battle, so headless specs never touch battle machinery. Task 110 (navigation events) should extend this result object. It also advances game time: 1 min to open a room, 0.25 to backtrack — game time is a float in minutes and `GameState.pack()` rounds it to a whole minute on save.
- `DungeonView.walkPath(path)` resolves `true` only if the party arrived; `false` on null path, encounter interruption, escape, or being superseded. Callers doing something on arrival (e.g. `stairsClicked`) must check it. Walking never blocks input (no halt cover): a click mid-walk starts a new walk that supersedes the old via a `currentWalk` token (superseded walks silently drop any encounter rolled on their last step), and Escape stops walking through `WindowManager`'s escape chain (`DungeonView.isWalking()`/`stopWalking()` sit above the main-menu fallback — don't add a competing Escape listener; the chain is the one owner of that key).
- Stairs are Angband-style: floors never persist; `setLevel(level, arrival)` spawns on a random `'up'` or `'down'` staircase. As of 2026-07-16 each direction gets 2–3 staircases in distinct rooms; `getStairs(direction)` returns a plain array of room indices — stairs carry no grid position (Room.getCenterTile was deleted; the view centers the glyph on the room's main box, `getBoxes()[0]`, by convention the first box). `stairsClicked` resolves its target room from the enclosing `.room` element's `data-index`, not by direction lookup. Stairs glyphs are children of their room element so they inherit hidden state.
- Door click pads were removed in task 120 (2026-07-18): doors and hanging doors themselves are the click targets for walking through (`doorClicked` reads `data-from`/`data-to` off the clicked element).
- Camera (task 111, 2026-07-16): `DungeonCamera` (views/dungeon) owns a rAF loop with critically damped springs (SmoothDamp) over **floor-coordinate space, not pixels**: state = focus point (tile units at viewport center) + scale, three independent scalars. Per frame it calls `DungeonViewport.applyCamera(focus, scale)` (single pixel projection: `location = viewportCenter − focus·gridSize·scale`); waking seeds from `DungeonViewport.deriveCamera()` (the inverse), so drags/instant centering hand off seamlessly. Pan and zoom targets compose — zoom mid-walk anchors on the party, idle zoom anchors on viewport center. Wheel zoom steps `scaleTarget` (viewport-tracked; `currentScale` is mid-glide fractional, never indexOf it) through `scaleSteps` → `DungeonCamera.zoomTo()`. Camera and party movement are fully decoupled: `walkPath` steps rooms on its own fixed beat (`stepTime` 250ms sleep) and fire-and-forgets `panTo(tile)` → `moveTo(point)` (void — nothing ever awaits the camera). Drag/reset call `DungeonCamera.stop()`; the old `setScale` is gone.
- Movement calls `DungeonFloorView.updateLocation(index, revealed)` (targeted class toggles); there is no full visibility pass — `drawDungeon()` bakes hide/current classes into `.room` elements at creation (reading `isRevealed` per element, since post-battle redraws happen mid-exploration). The floor is never redrawn on movement. Highlights must be flat background colors — box-shadow glows break on L-shaped rooms (two overlapping inner boxes).
- Corridor factories return `{ feature, doorTiles }` (not finished doors) — `FloorFactory` registers the corridor, paints the grid, then builds doors via `FloorFactorySupport.buildDoorToFeature`, because the corridor's room index doesn't exist until registration.
