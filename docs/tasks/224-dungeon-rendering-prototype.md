A throwaway prototype to find out if the dungeon view can support three effects before committing to them as part of
the move to grid movement ([215] Grid Based Dungeon Movement). The prototype should be a standalone page and should not
touch the existing dungeon view. It can read a real floor layout from `debug/floor-state.json` (generated by
`debug/headless-floor.js`) so we're testing against real room shapes, round and chamfered rooms included. The question
we're answering is how it looks and feels, and whether it holds 60fps in Electron. It doesn't need to be clean code.

In the floor state each door is `{ position, direction, from, to, open }`, sitting on the north or west wall of its position tile, and a room's `stairs` is `{ direction, x, y }` in the room's own coordinates (or null). See `docs/reference/dungeon-floor.md`.

## 1. Tile movement with a smooth camera
- The player marker moves one tile per key press (arrow keys / WASD) and is blocked by walls and closed doors.
- The marker's drawn position eases toward its tile with a critically damped spring (the SmoothDamp in
  `views/dungeon/dungeon-camera.js` already does this). It must not overshoot, because the vision polygon is cast from
  the marker's drawn position and an overshoot would let it see around corners.
- The camera follows the marker. Pan by transforming a container group, never by rebuilding the SVG.
- Holding a key should chain steps smoothly by retargeting the spring without stopping.

## 2. Vision mask
- Each frame, compute a 2D visibility polygon from the marker's *drawn* (interpolated) position against the wall
  segments. See Red Blob Games' "2D Visibility" article: sort segment endpoints by angle and sweep. Doors are
  segments, open doorways are gaps. (Doors now have an `open` flag in the floor state. They all start closed and open when walked through.) Only consider segments within a bounding box around the light radius.
- Walking from a corridor through a doorway into a large room should visibly widen the cone as the marker crosses the
  threshold. That's the effect we're looking for.
- The polygon is only cosmetic. Monsters aren't on the map, so there's no gameplay field of view to keep in sync, but
  tracking explored tiles per tile for the remembered map is fine.
- No blur. Build the mask as a single SVG `<mask>` (or `<clipPath>`) whose path `d` is rewritten every frame. The light
  radius falloff can be a radial gradient or a couple of concentric opacity steps.
- Areas seen before but not currently visible are drawn dimmed (a low-opacity dark layer). Areas never seen are hidden.

## 3. Layered parallax depth
Draw the map as stacked layers instead of one SVG per room: floor, then walls/doors, then higher features (columns).
Each layer is scaled up slightly around the camera focus, so the further something is from the center of the view the
more its upper layers push outward, which gives a fake 3D look.
- The scale for a layer is `1 + height * k`. Each layer is one group with one transform (translate to the focus, scale,
  translate back), so the cost per frame is one transform per layer and doesn't grow with tile count.
- If walls are only a single raised layer they'll look like floating lids. Try stacking several copies of the wall
  geometry at small height steps, with the lower copies darker, to fake the wall faces. Tune how many layers it takes
  before it reads as solid versus what it costs.
- Columns are the simplest test: a stack of circles.
- The vision mask has to line up with the layers. Try defining the mask in world coordinates and applying it inside each
  layer group, so it scales with that layer. Check whether wall tops near the edge of the view look right when they
  shift into or out of the visible area.
- This probably means splitting the room SVGs into per-layer geometry for the whole floor (all floors in one layer, all
  walls in another). Note how hard that would be to do in the real view.

## What to report back
- Frame timing (Chrome DevTools performance panel) for each effect on its own and all together, on a large room and a
  long corridor. Specifically, what does rewriting the mask path cost, and what does rasterizing the layers cost.
- Anything that would push this to canvas instead of SVG (for example, fog on a canvas overlay above SVG layers).
- Screenshots or a short recording of the doorway effect and the parallax.
